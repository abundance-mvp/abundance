## Overview

Stage 3.4 expands the client-side search functionality to search across all text fields in the Item model, rather than just `category` and `color`. This ensures users can find items by any attribute: name, brand, model, subCategory, material, etc.

**Goals:**
- Expand `filteredItems` computed property to search all searchable text fields
- Maintain fast client-side filtering (< 100ms latency)
- Show appropriate empty state when search yields no results
- Comprehensive test coverage for search functionality

**Non-Goals:**
- Server-side search (post-MVP)
- Fuzzy matching / typo tolerance
- Search history / suggestions
- Advanced filter UI (category dropdowns, etc.)

### 2. Item+Search.swift (New File)

**Path:** `/Users/w/code/abundance-mvp/Sources/Persistence/Models/Item+Search.swift`

**Purpose:** Encapsulate search matching logic in a testable extension.

```swift
// Sources/Persistence/Models/Item+Search.swift

import Foundation

extension Item {
    /// Returns true if the item matches the search query.
    /// Searches across: name, category, subCategory, brand, model, color, material
    ///
    /// - Parameter query: The search text to match against
    /// - Returns: True if any searchable field contains the query (case-insensitive)
    public func matchesSearchQuery(_ query: String) -> Bool {
        guard !query.isEmpty else { return true }

        // Collect all searchable text fields
        let searchableFields: [String?] = [
            name,
            category,
            subCategory,
            brand,
            model,
            color,
            material
        ]

        // Return true if any field contains the query (case-insensitive, locale-aware)
        return searchableFields.contains { field in
            field?.localizedCaseInsensitiveContains(query) == true
        }
    }

    /// All searchable field names for documentation/testing
    public static var searchableFieldNames: [String] {
        ["name", "category", "subCategory", "brand", "model", "color", "material"]
    }
}
```

**Design Decisions:**

1. **Extension Pattern:** Keeps Item model clean while adding search behavior
2. **`localizedCaseInsensitiveContains`:** Uses Apple's recommended locale-aware search
3. **Array of optionals:** Easy to extend when new fields are added
4. **`searchableFieldNames`:** Self-documenting for tests and future maintenance
5. **Public visibility:** Allows testing from test target

**Apple Documentation Reference:**
- `StringProtocol.localizedCaseInsensitiveContains(_:)` - Returns a Boolean value indicating whether the given string is non-empty and contained within this string by case-insensitive, non-literal search, taking into account the current locale.

## Edge Cases to Handle

### 1. Empty Search Query
- **Behavior:** Return all items
- **Implementation:** `guard !searchText.isEmpty else { return viewModel.items }`

### 2. All Fields Nil
- **Behavior:** Item does not match any search query
- **Implementation:** `field?.localizedCaseInsensitiveContains(query) == true` returns false for nil

### 3. Whitespace-Only Query
- **Current Behavior:** Treated as non-empty, no matches
- **Future Enhancement:** Could trim whitespace before search
- **Decision:** Keep current behavior for MVP, document as known behavior

### 4. Special Characters
- **Behavior:** `localizedCaseInsensitiveContains` handles Unicode correctly
- **Examples:** "cafe" matches "caf", accented characters handled

### 5. Very Long Search Queries
- **Behavior:** Works correctly, just won't match
- **Performance:** O(n * m) where n = items, m = fields; negligible for <500 items

### 6. Rapid Typing (Debouncing)
- **Current:** No debouncing in view-level filtering
- **Impact:** Instant filtering is desirable for < 500 items
- **Decision:** No debouncing needed for client-side filter

## Performance Considerations

### Client-Side Search Performance

**Assumptions:**
- MVP users: < 500 items
- 7 searchable fields per item
- Average field length: 20 characters

**Analysis:**
- `localizedCaseInsensitiveContains` is O(n * m) for string matching
- Total operations: 500 items x 7 fields = 3,500 string comparisons
- Expected latency: < 10ms on modern iOS devices

**No optimization needed** for MVP scale.

### Future Optimization (Post-MVP)

If scale increases:
1. **Debounce search input** - 300ms delay before filtering
2. **Precompute lowercase strings** - Avoid repeated lowercasing
3. **Server-side search** - Algolia or Firestore full-text search
4. **Search index** - Build inverted index on client
