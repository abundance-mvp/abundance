## Implementation Tasks

### Task 1: Choose SwiftUI Architecture Pattern

**Objective**: Select architecture pattern (MVVM, TCA, or MV) for Abundance iOS app

**Decision Criteria**:
1. **Team Size**: Single developer (early stage)
2. **Complexity**: Moderate (5-10 screens, real-time sync, async AI processing)
3. **Testability**: Must support 80% unit test coverage
4. **Maintainability**: Pattern should be well-documented and familiar
5. **SwiftUI Alignment**: Pattern should leverage SwiftUI's strengths (not fight them)

**Options Evaluation**:

#### Option A: MVVM (Model-View-ViewModel)

**Structure**:
```swift
// Model (data)
struct CatalogItem: Codable, Identifiable {
    let id: String
    var name: String
    var category: String
    // ...
}

// ViewModel (business logic + state)
@MainActor
class CatalogViewModel: ObservableObject {
    @Published var items: [CatalogItem] = []
    @Published var isLoading: Bool = false
    @Published var error: Error?

    private let repository: CatalogRepository

    init(repository: CatalogRepository) {
        self.repository = repository
    }

    func fetchItems() async {
        isLoading = true
        defer { isLoading = false }

        do {
            items = try await repository.fetchItems()
        } catch {
            self.error = error
        }
    }
}

// View (UI)
struct CatalogView: View {
    @StateObject private var viewModel: CatalogViewModel

    var body: some View {
        List(viewModel.items) { item in
            CatalogItemRow(item: item)
        }
        .task { await viewModel.fetchItems() }
    }
}
```

**Pros**:
- ✅ Standard pattern (most iOS developers familiar)
- ✅ Good testability (ViewModels are POJO, easy to unit test)
- ✅ SwiftUI-native (`@Published`, `@StateObject`, `@ObservedObject`)
- ✅ Async/await support (Swift 6 concurrency)

**Cons**:
- ⚠️ Boilerplate (ViewModels for every screen)
- ⚠️ State management can become complex (multiple ViewModels, shared state)

**Best For**: Standard iOS apps with moderate complexity

---

#### Option B: TCA (The Composable Architecture)

**Structure**:
```swift
import ComposableArchitecture

// State
struct CatalogState: Equatable {
    var items: [CatalogItem] = []
    var isLoading: Bool = false
    var error: Error?
}

// Action
enum CatalogAction {
    case fetchItems
    case itemsResponse(TaskResult<[CatalogItem]>)
}

// Reducer
struct CatalogReducer: ReducerProtocol {
    @Dependency(\.catalogClient) var catalogClient

    func reduce(into state: inout CatalogState, action: CatalogAction) -> EffectTask<CatalogAction> {
        switch action {
        case .fetchItems:
            state.isLoading = true
            return .task {
                await .itemsResponse(TaskResult { try await catalogClient.fetchItems() })
            }
        case .itemsResponse(.success(let items)):
            state.items = items
            state.isLoading = false
            return .none
        case .itemsResponse(.failure(let error)):
            state.error = error
            state.isLoading = false
            return .none
        }
    }
}

// View
struct CatalogView: View {
    let store: StoreOf<CatalogReducer>

    var body: some View {
        WithViewStore(self.store, observe: { $0 }) { viewStore in
            List(viewStore.items) { item in
                CatalogItemRow(item: item)
            }
            .onAppear { viewStore.send(.fetchItems) }
        }
    }
}
```

**Pros**:
- ✅ Excellent testability (pure functions, easy to test reducers)
- ✅ Unidirectional data flow (predictable state changes)
- ✅ Composability (feature modules combine easily)
- ✅ Built-in dependency injection (`@Dependency`)

**Cons**:
- ❌ Steep learning curve (new pattern, functional programming concepts)
- ❌ Boilerplate (State, Action, Reducer, Environment for every feature)
- ❌ Over-engineered for MVP (single developer, 5-10 screens)
- ⚠️ Third-party dependency (adds complexity, maintenance burden)

**Best For**: Large teams, complex apps with many features and shared state

#### Option C: MV (Model-View) - SwiftUI-Native

**Structure**:
```swift
// Model (data + logic)
@Observable
class CatalogModel {
    var items: [CatalogItem] = []
    var isLoading: Bool = false
    var error: Error?

    private let repository: CatalogRepository

    init(repository: CatalogRepository) {
        self.repository = repository
    }

    func fetchItems() async {
        isLoading = true
        defer { isLoading = false }

        do {
            items = try await repository.fetchItems()
        } catch {
            self.error = error
        }
    }
}

// View (UI)
struct CatalogView: View {
    @State private var model: CatalogModel

    var body: some View {
        List(model.items) { item in
            CatalogItemRow(item: item)
        }
        .task { await model.fetchItems() }
    }
}
```

**Pros**:
- ✅ Simplest pattern (minimal boilerplate)
- ✅ SwiftUI-native (`@Observable` macro in Swift 6)
- ✅ Good testability (model is POJO, async functions testable)
- ✅ Fast iteration (less code to write)

**Cons**:
- ⚠️ Less separation (model contains both data + logic)
- ⚠️ Not widely adopted yet (Swift 6 `@Observable` is new)

**Best For**: Small teams, MVP apps, rapid prototyping

---

**Recommendation: MVVM (Option A)**

**Rationale**:
1. **Team Size**: Single developer → MVVM is familiar, well-documented
2. **Testability**: ViewModels are easy to unit test (80% coverage target achievable)
3. **SwiftUI Alignment**: `@Published`, `@StateObject`, `@ObservedObject` are SwiftUI-native
4. **Maintainability**: Standard pattern → easier to onboard future developers
5. **Async/Await**: MVVM works well with Swift 6 concurrency
6. **Not Over-Engineered**: TCA is overkill for MVP (5-10 screens)
7. **Not Under-Engineered**: MV is too simple for complex state (real-time Firestore sync, AI processing)

**ADR to Create**: `ADR-010-swiftui-architecture-pattern.md` (Document MVVM choice with justification)

### Task 3: Design State Management Strategy

**Objective**: Choose state management approach for SwiftUI views

**Options**:
1. **Combine** (reactive publishers, `@Published` properties)
2. **async/await** (Swift 6 concurrency, tasks)
3. **@Observable** (Swift 6 macro, SwiftUI-native)

**Recommendation: Combine + async/await (Hybrid)**

**Rationale**:
- Use `@Published` for UI state (loading, error, data)
- Use `async/await` for asynchronous operations (network, Firestore, Vision)
- Best of both worlds: reactive UI updates + modern concurrency

**Example**:
```swift
@MainActor
class CatalogViewModel: ObservableObject {
    // Combine (reactive UI updates)
    @Published var items: [CatalogItem] = []
    @Published var isLoading: Bool = false
    @Published var error: Error?

    private let repository: CatalogRepository

    init(repository: CatalogRepository) {
        self.repository = repository
    }

    // async/await (asynchronous operations)
    func fetchItems() async {
        isLoading = true
        defer { isLoading = false }

        do {
            items = try await repository.fetchItems()
        } catch {
            self.error = error
        }
    }

    // Combine (Firestore real-time listener)
    func observeItems() {
        repository.observeItems()
            .receive(on: DispatchQueue.main)
            .sink { [weak self] items in
                self?.items = items
            }
            .store(in: &cancellables)
    }
}
```

### Task 4: Design Dependency Injection Strategy

**Objective**: Plan how to inject dependencies (repositories, services) into ViewModels

**Options**:
1. **Constructor Injection** (manual, pass dependencies via init)
2. **@EnvironmentObject** (SwiftUI environment, pass down view hierarchy)
3. **Property Wrappers** (custom `@Injected` wrapper, service locator pattern)

**Recommendation: Constructor Injection (Option 1)**

**Rationale**:
- ✅ Explicit dependencies (easy to see what ViewModel needs)
- ✅ Testable (pass mocks via init in tests)
- ✅ Type-safe (compiler checks dependencies)
- ✅ No magic (no service locator, no global state)

**Example**:
```swift
// Protocol (for testability)
protocol CatalogRepository {
    func fetchItems() async throws -> [CatalogItem]
    func observeItems() -> AnyPublisher<[CatalogItem], Never>
}

// Real implementation (Firestore)
class FirestoreCatalogRepository: CatalogRepository {
    private let db: Firestore

    init(db: Firestore = Firestore.firestore()) {
        self.db = db
    }

    func fetchItems() async throws -> [CatalogItem] {
        let snapshot = try await db.collection("items").getDocuments()
        return snapshot.documents.compactMap { try? $0.data(as: CatalogItem.self) }
    }
}

// ViewModel (constructor injection)
class CatalogViewModel: ObservableObject {
    private let repository: CatalogRepository

    init(repository: CatalogRepository) {
        self.repository = repository
    }
}

// View (pass dependency)
struct CatalogView: View {
    @StateObject private var viewModel: CatalogViewModel

    init(repository: CatalogRepository = FirestoreCatalogRepository()) {
        _viewModel = StateObject(wrappedValue: CatalogViewModel(repository: repository))
    }
}

// Test (mock injection)
class CatalogViewModelTests: XCTestCase {
    func testFetchItems() async {
        let mockRepo = MockCatalogRepository()
        let viewModel = CatalogViewModel(repository: mockRepo)
        await viewModel.fetchItems()
        XCTAssertEqual(viewModel.items.count, 1)
    }
}
```

### Task 5: Design Firebase SDK Integration

**Objective**: Design how iOS app integrates with Firebase services

**Firebase Services Used**:
1. **Firebase Authentication** (Apple Sign-In)
2. **Cloud Firestore** (catalog data, real-time sync)
3. **Firebase Storage** (photo uploads)
4. **Firebase Analytics** (user behavior tracking)

**Integration Patterns**:

#### 5.1 Firebase Authentication (Apple Sign-In)

**Flow**:
1. User taps "Sign in with Apple" button
2. iOS presents `ASAuthorizationController`
3. User authenticates with Face ID/Touch ID
4. iOS receives `ASAuthorizationAppleIDCredential` (contains ID token)
5. App exchanges Apple ID token for Firebase ID token
6. App stores Firebase ID token in Keychain
7. App uses Firebase ID token for API requests (Bearer token)

**Code Example**:
```swift
import AuthenticationServices
import FirebaseAuth

class AuthViewModel: ObservableObject {
    @Published var user: User?
    @Published var isLoading: Bool = false
    @Published var error: Error?

    func signInWithApple() {
        let request = ASAuthorizationAppleIDProvider().createRequest()
        request.requestedScopes = [.fullName, .email]

        let controller = ASAuthorizationController(authorizationRequests: [request])
        controller.delegate = self
        controller.performRequests()
    }
}

extension AuthViewModel: ASAuthorizationControllerDelegate {
    func authorizationController(controller: ASAuthorizationController, didCompleteWithAuthorization authorization: ASAuthorization) {
        if let appleIDCredential = authorization.credential as? ASAuthorizationAppleIDCredential {
            guard let appleIDToken = appleIDCredential.identityToken,
                  let idTokenString = String(data: appleIDToken, encoding: .utf8) else {
                return
            }

            let credential = OAuthProvider.credential(withProviderID: "apple.com", idToken: idTokenString, rawNonce: nonce)

            Task {
                do {
                    let authResult = try await Auth.auth().signIn(with: credential)
                    await MainActor.run {
                        self.user = authResult.user
                    }
                } catch {
                    await MainActor.run {
                        self.error = error
                    }
                }
            }
        }
    }
}
```

#### 5.2 Cloud Firestore (Real-Time Sync)

**Collections**:
- `users/{userId}` - User profile, subscription status
- `items/{itemId}` - Catalog items (name, category, location, etc.)

**Real-Time Listener Pattern**:
```swift
import FirebaseFirestore

class FirestoreCatalogRepository: CatalogRepository {
    private let db = Firestore.firestore()
    private var listener: ListenerRegistration?

    func observeItems(userId: String) -> AnyPublisher<[CatalogItem], Never> {
        let subject = PassthroughSubject<[CatalogItem], Never>()

        listener = db.collection("items")
            .whereField("userId", isEqualTo: userId)
            .addSnapshotListener { snapshot, error in
                guard let snapshot = snapshot else {
                    subject.send([])
                    return
                }

                let items = snapshot.documents.compactMap { doc -> CatalogItem? in
                    try? doc.data(as: CatalogItem.self)
                }

                subject.send(items)
            }

        return subject.eraseToAnyPublisher()
    }

    func stopObserving() {
        listener?.remove()
    }
}
```

**Offline Support** (Firestore automatically caches data):
```swift
// Enable offline persistence (in AppDelegate or App init)
let settings = FirestoreSettings()
settings.isPersistenceEnabled = true
Firestore.firestore().settings = settings
```

#### 5.3 Firebase Storage (Photo Uploads)

**Upload Flow**:
1. User captures photo with camera
2. Vision Framework crops object from photo (bounding box)
3. App uploads cropped image to Firebase Storage
4. Storage returns public HTTPS URL (signed URL, 1-hour expiration)
5. App sends URL to backend API (`POST /api/v1/items`)

**Code Example**:
```swift
import FirebaseStorage

class StorageService {
    private let storage = Storage.storage()

    func uploadImage(_ image: UIImage, userId: String, itemId: String) async throws -> URL {
        guard let imageData = image.jpegData(compressionQuality: 0.8) else {
            throw StorageError.invalidImage
        }

        let ref = storage.reference().child("users/\(userId)/items/\(itemId)/image.jpg")

        let metadata = StorageMetadata()
        metadata.contentType = "image/jpeg"

        _ = try await ref.putDataAsync(imageData, metadata: metadata)

        let downloadURL = try await ref.downloadURL()
        return downloadURL
    }
}
```

### Task 6: Design Vision Framework Integration

**Objective**: Design how iOS app uses Vision Framework for on-device object detection and barcode scanning

**Vision Framework APIs** (from TECH-STACK-MAP-001):

2. `VNDetectBarcodesRequest` - Barcode scanning (24 symbologies)
3. `VNImageRequestHandler` - Process image with Vision requests

**Integration Pattern**:

```swift
import Vision
import CoreML

class VisionService {
    private var model: VNCoreMLModel?

    init() {
        do {
            // Load YOLOv3-Tiny Core ML model
            let config = MLModelConfiguration()
            let yolo = try YOLOv3Tiny(configuration: config)
            model = try VNCoreMLModel(for: yolo.model)
        } catch {
            print("Failed to load Core ML model: \(error)")
        }
    }

    // Object Detection
    func detectObjects(in image: UIImage) async throws -> [DetectedObject] {
        guard let cgImage = image.cgImage, let model = model else {
            throw VisionError.invalidInput
        }

        let request = VNCoreMLRequest(model: model)
        request.imageCropAndScaleOption = .centerCrop

        let handler = VNImageRequestHandler(cgImage: cgImage, options: [:])
        try handler.perform([request])

        guard let results = request.results as? [VNRecognizedObjectObservation] else {
            return []
        }

        return results.compactMap { observation in
            guard observation.confidence > 0.5 else { return nil }

            let boundingBox = observation.boundingBox
            let label = observation.labels.first?.identifier ?? "unknown"

            return DetectedObject(
                label: label,
                confidence: observation.confidence,
                boundingBox: boundingBox
            )
        }
    }

    // Barcode Scanning
    func detectBarcodes(in image: UIImage) async throws -> [String] {
        guard let cgImage = image.cgImage else {
            throw VisionError.invalidInput
        }

        let request = VNDetectBarcodesRequest()

        let handler = VNImageRequestHandler(cgImage: cgImage, options: [:])
        try handler.perform([request])

        guard let results = request.results as? [VNBarcodeObservation] else {
            return []
        }

        return results.compactMap { $0.payloadStringValue }
    }
}

struct DetectedObject {
    let label: String
    let confidence: Float
    let boundingBox: CGRect
}
```

import Alamofire

protocol APIClient {

class FirebaseAPIClient: APIClient {
    private let baseURL = "https://us-central1-abundance-prod.cloudfunctions.net/api/v1"

    private func getAuthToken() async throws -> String {
        guard let user = Auth.auth().currentUser else {
            throw APIError.notAuthenticated
        }
        return try await user.getIDToken()
    }

    func createItem(_ item: CatalogItem) async throws -> CatalogItem {
        let token = try await getAuthToken()

        let headers: HTTPHeaders = [
            "Authorization": "Bearer \(token)",
            "Content-Type": "application/json"
        ]

        let response = try await AF.request(
            "\(baseURL)/items",
            method: .post,
            parameters: item,
            encoder: JSONParameterEncoder.default,
            headers: headers
        )
        .serializingDecodable(CatalogItem.self)
        .value

        return response
    }

    func listItems(page: Int = 1, limit: Int = 50) async throws -> [CatalogItem] {
        let token = try await getAuthToken()

        let headers: HTTPHeaders = [
            "Authorization": "Bearer \(token)"
        ]

        let parameters: [String: Any] = [
            "page": page,
            "limit": limit
        ]

        let response = try await AF.request(
            "\(baseURL)/items",
            method: .get,
            parameters: parameters,
            headers: headers
        )
        .serializingDecodable([CatalogItem].self)
        .value

        return response
    }
}

import Security

class KeychainService {
    func save(_ token: String, for key: String) throws {
        let data = token.data(using: .utf8)!

        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrAccount as String: key,
            kSecValueData as String: data
        ]

        SecItemDelete(query as CFDictionary)
        let status = SecItemAdd(query as CFDictionary, nil)

        guard status == errSecSuccess else {
            throw KeychainError.saveFailed
        }
    }

#### Risk 2: Firebase SDK Version Compatibility

**Description**: Firebase iOS SDK 11.5.0+ may have breaking changes with Swift 6

**Impact**: High (blocker if incompatible)

**Probability**: Low (Firebase maintains Swift compatibility)

**Mitigation**:
- Test Firebase integration early in Stage 3.1 (implementation research)
- Monitor Firebase iOS SDK release notes
- Have fallback to Firebase SDK 10.x if needed

---

#### Risk 3: Vision Framework Performance on Older Devices

**Description**: iPhone 15 Pro requirement may limit user base

**Impact**: Medium (market size)

**Probability**: Medium (iOS 26 adoption rate unknown)

**Mitigation**:
- Track iOS 26 adoption rates (public data)
- Consider fallback to iOS 25 if adoption is slow (ADR-004 may need revision)
- Ensure Vision Framework gracefully degrades on older devices

---

#### Risk 4: Test Coverage Gap (Integration Tests)

**Description**: Firebase Emulator setup may be complex, delaying integration tests

**Impact**: Medium (quality risk)

**Probability**: Medium (emulator setup has known issues)

**Mitigation**:
- Document Firebase Emulator setup in Stage 3.1 (implementation research)
- Prioritize unit tests (80%) over integration tests (15%) for MVP
- Use mocks for Firestore in unit tests (faster than emulator)
