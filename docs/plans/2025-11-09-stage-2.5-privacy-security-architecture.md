- Map each STRIDE category to Abundance components (iOS, Firebase, GCP, AI APIs)
- Identify attack vectors (e.g., "Attacker uploads malicious image to exhaust Gemini quota")
- Assess risk level (High/Medium/Low based on impact × probability)

- Reference research validation claims for each mitigation

  - Automated security rules testing in CI/CD pipeline (P0)

**Code Example** (Keychain storage):
```swift
import Security

class KeychainManager {
    func storeToken(_ token: String, forKey key: String) throws {
        let data = token.data(using: .utf8)!
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrAccount as String: key,
            kSecValueData as String: data,
            kSecAttrAccessible as String: kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly
        ]

        // Use AES-256-GCM via Secure Enclave (verified in RESEARCH-VALIDATION-stage-2.5.md)
        let status = SecItemAdd(query as CFDictionary, nil)
        guard status == errSecSuccess else {
            throw KeychainError.saveFailed(status)
        }
    }
}
```

```javascript
// OLD (INCORRECT): 7-day signed URL generated on iOS upload
// Problem: Violates privacy principle (images accessible for 7 days)

// NEW (CORRECT): Server-side signed URL generation with 2-5 minute expiration
async function generateShortLivedSignedUrl(imagePath) {
  const bucket = getStorage().bucket();
  const file = bucket.file(imagePath);

  const [url] = await file.getSignedUrl({
    version: 'v4',
    action: 'read',
    expires: Date.now() + 300000 // 5 minutes (verified 7-day max in RESEARCH-VALIDATION-stage-2.5.md, Claim 8)
  });

  return url; // Pass to SerpAPI immediately
}
```

### Task 5: Authentication & Authorization Architecture

**Objective**: Document complete authentication and authorization strategy with security best practices.

**Authentication Flow** (verified in RESEARCH-VALIDATION-stage-2.5.md, Claim 2):
1. User taps "Sign in with Apple"
2. ASAuthorizationController presents Face ID/Touch ID prompt (OAuth 2.0)
3. iOS returns ASAuthorizationAppleIDCredential (ID token)
4. App exchanges Apple token for Firebase ID token
5. Firebase ID token stored in Keychain (AES-256-GCM encryption)
6. Token refresh: Automatic (1 hour expiration), refresh token in Keychain

**Authorization Patterns**:
- **Firestore**: `request.auth.uid == resource.data.userId` (row-level security, verified Claim 6)
- **Firebase Storage**: `request.auth.uid == userId` in path (user folder isolation)
- **Cloud Functions**: Bearer token validation via `admin.auth().verifyIdToken()`
- **Premium Features**: Custom claims `request.auth.token.premium == true`

**Session Management**:
- **Token Expiration**: 1 hour (Firebase default)
- **Refresh Strategy**: Automatic via Firebase SDK
- **Logout**: Delete Keychain tokens, revoke Firebase session
- **Timeout**: No automatic timeout (session persists until logout)

  - Option: Configure Firebase Auth to use EU region if available
- **Timeline**: Complete before EU user beta testing (Month 4)

#### Risk 2: Firebase Misconfiguration Despite Testing
- **Impact**: High (privacy breach, GDPR violation)
- **Probability**: Low (automated testing + manual checklist)
- **Mitigation**:
  - Automated security rules tests in CI/CD (P0)
  - Firebase Security Review Checklist (P0)
  - External security audit (optional for MVP, recommended for v1.0)
  - Monitoring: Cloud Logging alerts for unauthorized access

#### Risk 3: Signed URL Architecture Change Breaks SerpAPI Integration
- **Impact**: Medium (Layer 2b product search fails)
- **Probability**: Low (architecture change is isolated to Cloud Function)
- **Mitigation**:
  - Test signed URL generation in Firebase Emulator Suite
  - Integration test: Generate signed URL → Pass to SerpAPI → Verify success
  - Fallback: Use 7-day signed URLs temporarily (document as technical debt)

#### Risk 4: Privacy Firewall Bypass via Code Change
- **Impact**: High (full photos uploaded, privacy violation)
- **Probability**: Very Low (automated testing, code review, privacy audit)
- **Mitigation**:
  - Automated test: Verify uploaded files < 500KB (CI/CD)
  - Firebase Storage rules: 10MB max upload (blocks full photos)
  - Privacy audit checklist (manual review before launch)

## Test-Driven Development Pattern

### Given/When/Then Examples

**Test Case 1: Firestore Security Rules - Unauthorized Read**
```
Given: User A is authenticated with uid="user_a"
  And: Item X has userId="user_b"
When: User A attempts to read Item X
Then: Firestore returns PermissionDenied error
  And: No data is returned
```

**Test Case 2: Privacy Firewall Validation**
```
Given: User captures photo (3MB) with AVCaptureSession
  And: Vision Framework detects 2 objects
When: User taps "Save" to catalog items
Then: 2 cropped objects (each < 500KB) uploaded to Firebase Storage
  And: Full photo (3MB) deleted from iOS temp directory
  And: Firebase Storage audit shows no files > 1MB
```

**Test Case 3: GDPR Right to Erasure**
```
Given: User has 10 catalog items with images in Firebase Storage
  And: User has AI metadata in Firestore (Gemini, SerpAPI, Claude results)
When: User requests account deletion
Then: Firestore user document deleted within 30 days
  And: All 10 items deleted from Firestore
  And: All images deleted from Firebase Storage (users/{userId}/ folder)
  And: AI metadata deleted (or anonymized if API retention required)
```
