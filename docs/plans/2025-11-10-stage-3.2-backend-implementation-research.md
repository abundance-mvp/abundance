## Verified Technical Constraints

From RESEARCH-VALIDATION-stage-3.2.md:

### Cloud Functions (2nd Gen)
- **Runtime**: Node.js 20 (production-ready, verified 2025-11-10)
- **Free Tier**: 2 million invocations/month, 400K GB-seconds compute
- **Pricing**: Resource-based (vCPU-second + GiB-second), NOT $0.40/million invocations
- **Cold Starts**: 2nd gen has faster cold starts than 1st gen (verified)
- **Triggers**: HTTP, Firestore (onCreate/onUpdate/onDelete), Cloud Scheduler

### Firestore
- **Free Tier**: 1GB storage, 50K reads/day, 20K writes/day (verified 2025-11-10)
- **Pricing**: $0.18/GB storage, $0.06/100K reads (verified)
- **Composite Indexes**: Supported, increase storage costs (optimize via Console)
- **Write Limit**: 500 writes/second with sequential field indexes (verified)
- **Offline Persistence**: Enabled by default on iOS SDK (verified)

### Firebase Storage
- **Pricing**: $0.020/GB Standard class us-central1 (verified 2025-11-10)
- **Signed URLs**: Time-limited max 2 weeks (NOT years as examples suggest)
- **Download URLs**: Token-based persistent URLs (alternative to signed URLs)
- **Cloud CDN**: $0.08/GB egress (blended estimate, verified)

### Firebase Admin SDK

### Task 2: Firestore Advanced Queries

**Objective**: Create query optimization examples (composite indexes, pagination, transactions).

**Sub-tasks**:
2.1. **Composite Index Example** (query userId + createdAt DESC)
   - firestore.indexes.json configuration
   - Query pattern: `items.where('userId', '==', uid).orderBy('createdAt', 'desc').limit(20)`
   - Index creation via Firebase Console
   - Performance comparison (single-field vs composite)

2.2. **Pagination Example** (cursor-based pagination)
   - startAfter() pattern for infinite scroll
   - Avoid offset-based pagination (scales poorly)
   - Return last document ID for next page

2.3. **Batch Write Example** (atomic updates)
   - Update multiple items in single transaction
   - Rollback on error
   - 500-document limit per batch

2.4. **Transaction Example** (concurrent write conflict resolution)
   - Read-modify-write pattern
   - Retry logic for transaction conflicts
   - Use case: Increment premium user count

**Acceptance Criteria**:
- All queries use composite indexes (no full collection scans)
- Pagination uses cursors (not offsets)
- Batch writes handle 500-document limit
- Transactions have retry logic (max 5 retries)

**Test Example**:
```javascript
// Given: 100 items for userId="abc123"
// When: Query with .limit(20).startAfter(lastDocId)
// Then: Returns next 20 items, no duplicate results
```

### Task 3: AI Pipeline Orchestration

**Objective**: Implement complete Layer 2a → 2b → 3 AI processing pipeline.

**Sub-tasks**:
3.1. **Layer 2a: Gemini Attribute Extraction**
   - Vertex AI Node.js SDK (@google-cloud/vertexai)
   - Gemini 2.5 Flash-Lite model invocation
   - JSON Schema Mode for structured output (color, material, condition, category)
   - Error handling (API timeout, quota exceeded)
   - Firestore update (write attributes to item.aiMetadata.layer2a)

3.2. **Layer 2b: Product Search (SerpAPI + UPCitemdb)**
   - Dual-mode strategy (barcode-first, visual fallback)
   - UPCitemdb REST API call (if barcode exists)
   - SerpAPI Google Lens REST API call (if no barcode or UPC lookup fails)
   - Axios/node-fetch HTTP client (no native SDK)
   - Parse visual_matches response (brand, model, price)
   - Firestore update (write product data to item.aiMetadata.layer2b)

3.3. **Layer 3: Claude Synthesis**
   - Anthropic Node.js SDK (@anthropic-ai/sdk)
   - Claude Sonnet 4.5 Batch API invocation
   - Merge Layer 2a + Layer 2b results
   - Conflict resolution (vision vs product search mismatches)
   - Confidence scoring (0.0 to 1.0)
   - Firestore update (write final metadata to item.aiMetadata.layer3, status="complete")

3.4. **Error Handling & Retry**
   - Exponential backoff (1s, 2s, 4s, 8s, 16s max retries)
   - Dead letter queue (Firestore collection: failedItems)
   - Mark item status="failed" with error message
   - Manual retry UI support (re-trigger from iOS app)

**Acceptance Criteria**:
- All AI API calls have timeout limits (30s max)
- All errors logged to Cloud Logging
- Failed items stored in failedItems collection
- Retry logic implements exponential backoff
- All API responses validated (schema check)

**Test Example**:


**Acceptance Criteria**:
- All Auth tokens verified before processing
- All Storage uploads use signed URLs (NOT public read)
- Custom claims reflect subscription status
- Storage lifecycle policies auto-delete old files

### Risks Identified

**Risk 1: Cloud Functions Pricing Model Changed**
- **Impact**: High (original cost estimates based on invocation-based pricing, now resource-based)
- **Probability**: High (verified in RESEARCH-VALIDATION-stage-3.2.md)
- **Mitigation**: Update cost model, use minimum instances sparingly, optimize function memory/CPU

**Risk 2: Gemini 2.5 Flash-Lite Pricing 4x Higher Than Expected**
- **Impact**: Medium (cost per item increased from $0.000249 to ~$0.001)
- **Probability**: High (verified in RESEARCH-VALIDATION-stage-3.2.md)
- **Mitigation**: Cost still acceptable ($76.10/month vs $6K revenue = 98.7% margin), no action needed

**Risk 3: Signed URLs Max 2-Week Expiration**
- **Impact**: Low (original examples suggested years, actually limited to 2 weeks)
- **Probability**: High (verified in RESEARCH-VALIDATION-stage-3.2.md)
- **Mitigation**: Use download URLs (token-based, persistent) for iOS app, signed URLs (time-limited) for SerpAPI only

**Risk 4: Firestore 500 Writes/Second Limit with Sequential Indexes**
- **Impact**: Medium (could throttle AI pipeline if many concurrent items processed)
- **Probability**: Low (MVP unlikely to hit 500 writes/second)
- **Mitigation**: Monitor write throughput, avoid sequential field indexes (use random IDs, not auto-incrementing)
