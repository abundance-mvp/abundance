### Decision 1: Client Platform - iOS-First (Swift 6.0, SwiftUI)

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| iOS-first (Swift 6, SwiftUI) | On-device Vision Framework, superior UX, App Store featuring, 2-3mo faster MVP | 30-40% U.S. market share, platform dependency | ✅ SELECTED |
| Cross-platform (React Native/Flutter) | 70%+ market from Day 1, single codebase | No Vision Framework access, inferior UX, no App Store featuring | ❌ REJECTED |
| Android-first | 60%+ U.S. market, emerging markets | Lower revenue potential, device fragmentation, no on-device ML equivalent | ❌ REJECTED |

**Justification:**

Per ADR-001, iOS-first enables:
- **Privacy-preserving architecture:** Apple Vision framework + Neural Engine for on-device segmentation (full photos never leave device)
- **Demographic alignment:** iOS users have $85K vs. $61K median income (ref: ADR-001)
- **App Store featuring:** iOS 26 launch window worth $500K-2M marketing equivalent (ref: ADR-001)
- **Development speed:** Single-platform MVP ships 2-3 months faster than cross-platform (ref: ADR-001)

**Verified Technology:**
- **Swift 6.3:** Released alongside iOS 26 in September 2025 (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 12)
- **iOS 26:** Released September 15, 2025, requires A13 Bionic or newer (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 11)

**Trade-offs Accepted:**
- 15% market at launch (iOS 26-only per ADR-004), expanding to 30% by Month 6, 40-50% by Month 12
- Platform dependency on Apple (mitigated by Android at Month 6-9)
- Higher iOS development expertise required

**ADR to Create:** ADR-005: iOS-First Platform Strategy (GCP Platform Choice)

### Decision 3: Backend Architecture - Monolith-First

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| Monolith-first | Faster MVP (5-6 months), simpler deployment, easier debugging | May require refactor at scale (50K+ users) | ✅ SELECTED |
| Microservices from Day 1 | "Future-proof," independent scaling, team isolation | 2-3× longer MVP timeline, premature complexity | ❌ REJECTED |
| Serverless-only (Cloud Functions) | Auto-scaling, pay-per-use, no server management | Cold start latency, function size limits, stateless constraints | ✅ VARIANT (Cloud Functions as monolith runtime) |

**Justification:**

**Martin Fowler's Monolith-First Pattern (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 16):**
> "Almost all successful microservice stories started with a monolith that got too big and was broken up. Almost all cases where system was built as microservices from scratch ended up in serious trouble."

**Why Monolith-First for Abundance:**

1. **Domain boundaries unclear:** Unknown which features will need independent scaling (inventory? marketplace? AI processing?)
2. **Team size:** 2-3 engineers cannot maintain multiple microservices effectively
3. **Iteration speed:** Monolith allows rapid changes without coordinating multiple services
4. **MVP timeline:** 5-6 months vs. 9-12 months for microservices architecture

**Implementation via Cloud Functions:**
- **Approach:** Single Cloud Function serves all API endpoints (monolithic function)
- **Routing:** Internal Express.js router handles `/api/inventory`, `/api/marketplace`, `/api/ai` routes
- **Deployment:** Single deployment unit (no orchestration complexity)
- **Future migration:** When scale requires, split monolith into separate functions (inventory-service, marketplace-service, ai-service)

**Refactoring Threshold (ref: ADR-003):**
- **Month 6:** 5,000 users (monolith sufficient)
- **Month 12:** 50,000 users (evaluate split if cold starts > 2 seconds)
- **Month 18:** 250,000 users (likely require microservices split)

**Trade-offs Accepted:**
- May require architectural refactor at 50K+ users (accept 6-8 week refactor cost vs. 3-6 month upfront microservices build)
- Single point of failure (mitigated by Cloud Functions auto-restart)
- No independent service scaling (mitigated by Cloud Functions auto-scale handles 5-50K users)

**ADR to Create:** ADR-006: Monolith-First Backend Architecture

### Decision 4: API Style - REST over HTTPS

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| REST | Simple, cacheable, 28% better battery life on mobile, 67% better offline caching | Over-fetching on complex queries | ✅ SELECTED |
| GraphQL | 41% less mobile data, 34% faster initial load, reduces over-fetching | 28% worse battery life, 33% slower average response time (922ms vs 1864ms) | ❌ REJECTED |
| gRPC | Fastest (binary), efficient, type-safe | Mobile support immature, debugging harder | ❌ REJECTED |

**Justification:**

**REST Advantages for Abundance MVP (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 17):**

1. **Battery Efficiency:** 28% better battery life (simpler processing) - critical for camera-heavy app
2. **Offline Caching:** 67% better offline caching support (HTTP caching headers) - important for inventory browsing
3. **Simpler Implementation:** Established patterns, easier onboarding for engineers
4. **Performance:** Average response time 922ms vs. 1864ms for GraphQL

**GraphQL Advantages (Why Not Selected):**
- 41% reduction in mobile data consumption
- 34% faster initial load times
- Reduces over-fetching (REST responses 340% larger on average)

**Why REST Wins for MVP:**
- **Simple CRUD operations:** Abundance MVP = inventory CRUD + AI enrichment + basic marketplace
- **No complex nested queries:** Not a social graph (Instagram uses GraphQL for complex friend-of-friend queries)
- **Battery life matters:** Camera + AI processing already tax battery; REST reduces overhead
- **Caching critical:** Users browse inventory offline; HTTP caching simpler than GraphQL caching

**REST API Design Principles:**
- **Resource-oriented:** `/items/{itemId}`, `/users/{userId}/inventory`, `/marketplace/listings`
- **Standard HTTP methods:** GET (read), POST (create), PUT (update), DELETE (remove)
- **JSON payloads:** `Content-Type: application/json`
- **Versioning:** `/api/v1/` prefix (enables future API changes)
- **Authentication:** Firebase Auth JWT tokens in `Authorization: Bearer <token>` header

**Future Consideration:**
- **Month 12+:** If marketplace adds complex social features (friend recommendations, activity feeds), evaluate GraphQL for those endpoints while keeping REST for inventory CRUD

**Trade-offs Accepted:**
- Over-fetching on list endpoints (e.g., `/inventory` returns full item objects, not just IDs)
- Multiple round trips for related data (e.g., get item → get owner profile separately)
- No real-time subscriptions (use Firestore listeners instead)

**ADR to Create:** ADR-007: REST API Design

### Decision 5: Database - Cloud Firestore (NoSQL Document Store)

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| Cloud Firestore | Real-time listeners, offline support, generous free tier, scales horizontally | No joins, limited query complexity, eventual consistency | ✅ SELECTED |
| Cloud SQL (PostgreSQL) | Relational integrity, complex queries, ACID transactions | No offline support, higher cost, manual scaling | ❌ REJECTED |
| Hybrid (Firestore + SQL) | Best of both worlds | Complexity, data sync challenges, higher cost | ❌ REJECTED (defer to Month 12+) |

**Justification:**

**Why Firestore for Abundance MVP:**

1. **Real-time sync:** Firestore listeners enable instant inventory updates across devices (user catalogs item on iPhone, sees on iPad immediately)
2. **Offline-first:** Client SDK caches data locally, syncs when online (critical for cataloging in basements/attics with poor signal)
3. **Free tier:** 50,000 reads, 20,000 writes/day = sufficient for 5,000 users (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 2)
4. **Horizontal scaling:** Auto-scales to millions of documents (no sharding required)
5. **Firebase SDK integration:** Single SDK for Auth + Firestore + Storage (reduces integration complexity)

**Firestore Limitations (Verified, ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 9):**
- **Query limitations:** Maximum 30 filter parameters per query, range queries limited to single field
- **No full-text search:** Requires Algolia extension or external search service
- **Write rate:** Maximum 1 write/second per document (not a constraint for inventory app)
- **No joins:** Must denormalize data (trade-off for performance)

**Data Model Design (High-Level):**

```
users/{userId}
  - email, displayName, createdAt, photoURL
  - tier: "free" | "premium"

items/{itemId}
  - ownerId: string (ref: users/{userId})
  - name: string
  - category: string
  - estimatedValue: number
  - photoUrls: array<string> (Firebase Storage URLs)
  - aiMetadata: {
      confidence: number
      attributes: {color, material, condition}
      brandInfo: {brand, model, variant}
    }
  - visibility: "private" | "showcase" | "shared" | "marketplace"
  - createdAt: timestamp

sharingCircles/{circleId}
  - name: string
  - members: array<string> (userIds)
  - createdBy: string
  - createdAt: timestamp

marketplaceListings/{listingId}
  - itemId: string (ref: items/{itemId})
  - sellerId: string (ref: users/{userId})
  - price: number
  - status: "active" | "sold" | "removed"
  - createdAt: timestamp
```

**Denormalization Strategy:**
- **Item owner info:** Store `ownerDisplayName` and `ownerPhotoURL` in `items` collection (avoid lookup on every list view)
- **Listing item preview:** Store `itemName`, `itemPhotoUrl` in `marketplaceListings` (avoid join on marketplace browse)

**Indexing Strategy:**
- **Composite index:** `items` collection on `(ownerId, createdAt DESC)` for user's inventory sorted by newest
- **Composite index:** `marketplaceListings` on `(status, createdAt DESC)` for active listings
- **Single-field index:** `items.category` for filtering

**Free Tier Capacity (5,000 users):**
- **Reads:** 50,000/day = 10 reads/user/day (sufficient for browsing inventory)
- **Writes:** 20,000/day = 4 writes/user/day (sufficient for cataloging ~2 items/day + updates)
- **Storage:** 1GB free = ~200,000 item documents (5K users × 50 items = 250K items fits with denormalization)

**Trade-offs Accepted:**
- No full-text search (add Algolia extension in Month 6-9 for ~$1/month)
- No complex analytics queries (use BigQuery export for analytics if needed)
- Eventual consistency (accept 1-2 second propagation delay for non-critical updates)
- Higher cost at scale (Firestore $0.18 per 100K reads vs. PostgreSQL $0.023/GB-month, but free tier covers MVP)

**ADR to Create:** ADR-008: Cloud Firestore Database

### Decision 6: Authentication - Firebase Authentication

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| Firebase Authentication | Free (50K MAUs), social logins, phone auth, easy Firebase SDK integration | Less customizable than Auth0 | ✅ SELECTED |
| Auth0 | Flexible, enterprise features, extensive customization | $0.015/MAU after 7K MAUs = $75/month at 5K users | ❌ REJECTED (cost) |
| Custom (JWT + Firestore) | Full control, no vendor lock-in | 8-12 weeks to build, security risks | ❌ REJECTED (time) |

**Justification:**

**Firebase Authentication Features:**
- **Email/password:** Standard authentication (free, unlimited)
- **Social logins:** Google, Apple Sign-In (free, unlimited) - critical for iOS users (Apple Sign-In required by App Store)
- **Phone/SMS:** 10,000 verifications/month free (sufficient for trust & safety phone verification)
- **Anonymous auth:** Allows users to try app before creating account (lowers signup friction)

**Free Tier (Verified, ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 1):**
- **50,000 MAUs:** Free for email/password and social logins
- **10,000 phone verifications/month:** Free (after: $0.01 per verification)
- **Cost at 5K users:** $0/month (well within free tier)

**Integration with Firestore:**
- **Security Rules:** Firestore rules use `request.auth.uid` to enforce row-level security
- **Custom claims:** Firebase Auth supports custom claims for roles (user, moderator, admin)
- **Token refresh:** Automatic token refresh (no manual refresh logic)

**Authentication Flow:**
1. User signs in via Apple Sign-In or email/password
2. Firebase Auth returns JWT token (1-hour expiry, auto-refreshes)
3. iOS app stores token in Keychain (secure enclave)
4. All API requests include `Authorization: Bearer <token>` header
5. Cloud Function verifies token via Firebase Admin SDK
6. If valid, request proceeds; if invalid, return 401 Unauthorized

**Trust & Safety (Phone Verification):**
- **Free tier:** 10,000 verifications/month (sufficient for 5K users × 2 verifications/user/year)
- **Use case:** Verify phone number for marketplace sellers (reduce fraud)
- **Implementation:** Firebase Auth phone verification via SMS

**Trade-offs Accepted:**
- Less customizable than Auth0 (cannot add custom authentication methods easily)
- Firebase vendor lock-in (if migrate to AWS, must rebuild auth)
- No built-in 2FA (can add via third-party or custom implementation in Phase 2)

**ADR to Create:** ADR-009: Firebase Authentication

### Decision 7: File Storage - Hybrid Strategy (Firebase Storage + Cloud CDN)

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| Firebase Storage + Cloud CDN | 5GB free (US regions), Firebase SDK integration, Cloud CDN for fast delivery | Requires Blaze plan ($0.026/GB above 5GB) | ✅ SELECTED |
| Pure Cloud Storage | Cheaper ($0.020/GB), no Firebase requirement | No iOS SDK integration, manual URL signing | ❌ REJECTED (complexity) |
| AWS S3 | Mature, $0.023/GB, global CDN | No Firebase integration, SerpAPI issues reported | ❌ REJECTED (GCP alignment) |

**Justification:**

**Critical Finding - Blaze Plan Requirement (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 4):**
- **As of October 30, 2024:** New Firebase projects require Blaze (pay-as-you-go) plan to provision Cloud Storage buckets
- **Free Tier Still Available:** 5GB storage in US-CENTRAL1, US-EAST1, US-WEST1 regions on Blaze plan
- **Cost Above Free Tier:** $0.026/GB storage + $0.12/GB download

**Storage Architecture:**

```
Firebase Storage Structure:
/users/{userId}/
  /original/        # Original photos (privacy: only owner can read)
    /{itemId}.jpg   # Full-resolution photo (never transmitted to cloud AI)
  /cropped/         # Cropped objects (privacy: owner + AI service can read)
    /{itemId}/{objectIndex}.jpg  # Individual objects segmented on-device
  /processed/       # Processed images (privacy: public if visibility=marketplace)
    /{itemId}_thumb.jpg   # Thumbnail (150x150)
    /{itemId}_medium.jpg  # Medium (600x600)
```

**Privacy Architecture:**
1. **Original photos:** Stored in `/users/{userId}/original/` with Firestore Security Rules: only owner can read
2. **Cropped objects:** On-device Vision Framework segments objects → uploads only cropped images to `/users/{userId}/cropped/`
3. **Cloud AI:** Accesses cropped images (not full photos) for enrichment
4. **Public URLs:** Only processed thumbnails/medium images have public URLs (for marketplace)

**Storage Cost Estimation (5K users, Month 6):**
- **Photos per user:** 50 items × 2 photos/item = 100 photos/user
- **Total photos:** 5,000 users × 100 photos = 500,000 photos
- **Storage needed:**
  - Original: 500K × 2MB = 1,000GB (never uploaded to cloud, stored on-device only) = $0
  - Cropped: 500K × 100KB = 50GB (uploaded for AI enrichment)
  - Processed (thumb + medium): 500K × 50KB = 25GB
  - **Total cloud storage:** 75GB
- **Cost:** 5GB free + (70GB × $0.026/GB) = **$1.82/month**

**Download Cost Estimation:**
- **Browsing:** 5,000 users × 50 item views/month × 50KB thumbnail = 12.5GB downloads/month
- **Cost:** $0.12/GB × 12.5GB = **$1.50/month**

**Total Storage Cost (Month 6):** $1.82 + $1.50 = **$3.32/month** (very affordable)

**Cloud CDN Integration:**
- Firebase Storage automatically serves files via Google Cloud CDN (no extra configuration)
- CDN caching reduces latency (50-200ms vs. 500ms+ without CDN)
- Public URLs format: `https://firebasestorage.googleapis.com/v0/b/{bucket}/o/{path}?alt=media`

**SerpAPI Integration (Stage 2.4 Consideration):**
- SerpAPI Google Lens requires **publicly accessible HTTPS URLs**
- Firebase Storage + Cloud CDN meets this requirement (ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 3, Issue 2)
- Alternative GCS + Cloud CDN also works (SerpAPI documentation recommends GCS over AWS S3 due to known issues)

**Trade-offs Accepted:**
- Blaze plan required (billing from Day 1, but cost minimal)
- Vendor lock-in to Firebase Storage (migration to S3 requires URL rewrite in all documents)
- No advanced features like object versioning (can add via Cloud Storage API if needed)

**ADR to Create:** ADR-010: Hybrid Storage Strategy (Firebase Storage + Cloud CDN)

### Decision 8: Compute - Cloud Functions (Node.js)

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| Cloud Functions (Node.js) | 2M invocations/month free, auto-scaling, simple deployment, Firebase triggers | Cold start latency (200ms avg), 9-minute timeout | ✅ SELECTED |
| Cloud Run | No cold start (minimum instances), containerized, flexible runtime | Requires Dockerfile, more complex setup | ❌ REJECTED (defer to Month 12+) |
| App Engine | Fully managed PaaS, auto-scaling | Less modern, Google recommends Cloud Run for new projects | ❌ REJECTED |

**Justification:**

**Cloud Functions Free Tier (Verified, ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 3):**
- **2M invocations/month:** Free (5,000 users × 40 API calls/user/month = 200K invocations, well within free tier)
- **400,000 GB-seconds compute:** Free (sufficient for lightweight CRUD operations)
- **5GB outbound data:** Free (API responses typically <1KB, 200K requests × 1KB = 200MB, well within free tier)

**Cloud Functions Performance (Verified, ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 10):**
- **Node.js cold start:** ~200ms average (acceptable for API endpoints)
- **Warm execution:** ~10-50ms (subsequent requests reuse same instance)
- **Mitigation strategies:** Lazy initialization, global variable caching, minimize dependencies

**Function Structure (Monolith-First):**

```javascript
// Monolithic Cloud Function (single deployment unit)
const express = require('express');
const admin = require('firebase-admin');

const app = express();
admin.initializeApp();

// Inventory routes
app.get('/api/v1/inventory', getInventory);
app.post('/api/v1/items', createItem);
app.put('/api/v1/items/:itemId', updateItem);
app.delete('/api/v1/items/:itemId', deleteItem);

// AI routes
app.post('/api/v1/ai/enrich', enrichItem);

// Marketplace routes (Phase 2)
app.get('/api/v1/marketplace/listings', getListings);
app.post('/api/v1/marketplace/offers', createOffer);

exports.api = functions.https.onRequest(app);
```

**Triggers:**
- **HTTP triggers:** REST API endpoints (public, authenticated via Firebase Auth)
- **Firestore triggers:** Background processing (e.g., `onCreate` for new items to trigger AI enrichment)
- **Storage triggers:** Image processing (e.g., generate thumbnails when photo uploaded)

**Runtime Selection (Node.js vs. Python):**
- **Node.js 20:** JavaScript runtime, smaller cold starts (~200ms), better for API endpoints
- **Python 3.11:** Slower cold starts (~500ms-1s), better for AI/ML libraries
- **Decision:** **Node.js 20** for main API function; separate Python function for AI processing if needed in Stage 2.4

**Scaling:**
- **Auto-scaling:** Cloud Functions automatically scales from 0 to N instances based on traffic
- **Concurrency:** Each function instance handles 1 request at a time (no concurrency within instance)
- **Maximum instances:** 1,000 default (configurable), sufficient for 5K-50K users

**Trade-offs Accepted:**
- Cold start latency (200ms for first request after idle period) vs. Cloud Run's minimum instances (no cold starts but higher cost)
- 9-minute timeout (sufficient for AI processing; if >9min needed, use Cloud Tasks)
- No persistent state (use Firestore for state)

**ADR to Create:** ADR-011: Cloud Functions Compute

### Decision 9: AI/ML Platform - Hybrid (On-Device Vision Framework + Cloud AI)

**Options Evaluated:**

| Option | Pros | Cons | Recommendation |
|--------|------|------|----------------|
| Hybrid (Vision Framework on-device + Gemini/Claude cloud) | Privacy-first, $0 free tier cost, best accuracy for premium | Complex multi-layer pipeline | ✅ SELECTED |
| Cloud-only (Gemini/GPT-4V) | Simpler architecture, best accuracy | No privacy, $0.02/image cost, unsustainable free tier | ❌ REJECTED |
| On-device only (Vision Framework) | Privacy, $0 cost | Lower accuracy, no product search | ❌ REJECTED (insufficient for premium tier) |

**Justification:**

**Privacy-First Architecture (ref: ADR-001, ADR-004):**

1. **Layer 1 (On-Device - iOS Vision Framework):**
   - **API:** VNCoreMLRequest with pre-trained Core ML model (YOLOv3-Tiny or iOS 26 Vision API)
   - **Function:** Object detection and segmentation (bounding boxes)
   - **Privacy:** Full wide-angle photos never leave device
   - **Cost:** $0 (on-device processing via Neural Engine)
   - **Latency:** <500ms on A17 Pro chip

2. **Layer 2a (Cloud - Gemini 2.5 Flash-Lite):**
   - **API:** Vertex AI Gemini API
   - **Function:** Attribute extraction (color, material, condition, category) from cropped object images
   - **Privacy:** Only cropped objects uploaded (not full room photos)
   - **Cost:** $0.000249/image (ref: abundance-analysis-pipeline-design.md, line 868)
   - **Latency:** 30-50ms

3. **Layer 2b (Cloud - Product Search):**
   - **API:** **TBD in Stage 2.4** (Google Shopping Graph API not found; alternatives: SerpAPI Google Lens, Cloud Retail API)
   - **Function:** Brand/model/price identification
   - **Privacy:** Only cropped objects uploaded
   - **Cost:** **TBD** (originally estimated $0.007/item, but API unverified)
   - **Latency:** **TBD** (SerpAPI Google Lens: 5-7s per abundance-analysis-pipeline-design.md line 876)

4. **Layer 3 (Cloud - Claude Sonnet 4.5):**
   - **API:** Anthropic Claude API
   - **Function:** AI synthesis (merge Layer 2a + 2b results, conflict resolution)
   - **Cost:** $0.0092/inference (ref: abundance-analysis-pipeline-design.md, line 883)
   - **Latency:** 1-2s

**Tier Structure:**

| Tier | Layers Used | Cost per Item | User Experience |
|------|-------------|---------------|-----------------|
| **Free Tier** | Layer 1 only (on-device Vision) | $0 | Basic object detection (chair, lamp, book), no brand/model/price |
| **Premium Tier** | Layer 1 + 2a + 2b + 3 (full pipeline) | $0.000249 + **$0.007 (TBD)** + $0.0092 = **~$0.017/item (TBD)** | Full enrichment (brand, model, price estimate, attributes) |

**Free Tier Economics:**
- **5,000 users × 50 items = 250,000 items**
- **Cost:** $0 (on-device only)
- **Margin:** 94% (ref: ADR-004)

**Premium Tier Economics (15% conversion = 750 users):**
- **750 users × 50 items = 37,500 items**
- **Cost:** 37,500 × $0.017 = **$637.50/month (estimated, pending API verification in Stage 2.4)**
- **Revenue:** 750 users × $8/month = $6,000/month
- **Margin:** (6000 - 637.50) / 6000 = **89%**

**Critical Issue - Google Shopping Graph API (ref: RESEARCH-VALIDATION-stage-2.1.md, Issue 3):**
- **Problem:** "Google Shopping Graph API" not found in public Google documentation
- **Possible Alternatives:**
  1. **Cloud Retail API:** $2.50 per 1,000 requests = $0.0025 per request (cheaper than estimated $0.007)
  2. **SerpAPI Google Lens:** Third-party API, pricing TBD
  3. **Content API for Shopping:** Merchant-focused, may not fit consumer use case
- **Action Required:** Stage 2.4 (Computer Vision & ML Expert) must research and verify actual product search API
- **Financial Risk:** If actual API costs significantly more than $0.007/item, premium tier economics may require adjustment

**Vertex AI Pricing (Verified, ref: RESEARCH-VALIDATION-stage-2.1.md, Claim 14):**
- **Gemini 2.5 Pro:** $1.25 per million input tokens (up to 200K context)
- **Automatic metrics:** $0.00003 per 1K characters input
- **New customers:** $300 free credits
- **Note:** Use Gemini 2.5 Flash-Lite (cheaper variant) for attribute extraction

**Trade-offs Accepted:**
- Complex multi-layer pipeline (4 layers) vs. simple cloud-only (1 API call)
- API verification deferred to Stage 2.4 (product search API uncertainty)
- Free tier has limited accuracy (no brand/model/price) - acceptable per ADR-002 (dual personas: Organizers value organization more than exact brand)

**ADR to Create:** ADR-012: Hybrid AI Strategy (On-Device Vision + Cloud AI) - WITH CAVEAT that Layer 2b API must be verified in Stage 2.4
