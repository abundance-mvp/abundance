# Stage 3.0: MVP Feature Completion Design

**Date:** 2026-01-14
**Status:** Approved
**Author:** Claude + W (brainstorming session)

## Overview

Stage 3.0 completes the MVP feature set for user testing. Building on Stage 2.7's @Observable migration and Liquid Glass styling, this stage adds the missing CRUD operations, schema alignment, and data integrity features.

## Goals

- Complete CRUD operations (edit, delete currently missing)
- Align iOS Item model with Gemini 3 Pro output schema
- Expand search to all item fields
- Capture photo metadata for fraud prevention
- Ship feature-complete MVP for user testing

## Non-Goals (Post-MVP)

- Soft delete / Recently Deleted
- Bulk edit operations
- Offline capture queue
- Push notifications for processing complete
- Server-side search / Algolia integration
- Metadata fraud enforcement gates

---

## Design Decisions

### 1. Schema Alignment

**Decision:** Expand Item model to match CatalogItem (flat structure)

**Rationale:**
- Single source of truth, simpler queries
- SwiftUI bindings work better with flat structures
- Firestore document is already flat - model should match
- Edit forms become straightforward

**Current Gap:**
- Item has 6 optional fields
- CatalogItem (Gemini output) has 12 fields
- Gemini output stored in separate `catalog` field, not merged

### 2. Field Editability

**Decision:** All fields user-editable EXCEPT AI metadata

**Editable fields:**
- name, category, subCategory, brand, model
- color, material, condition, dimensions
- quantity, estimatedValue

**Read-only (AI metadata):**
- confidence, processingNotes

**Rationale:** Users know their items; AI makes mistakes on obscure items. But confidence scores are AI assessments, not item attributes.

### 3. Edit Flow (Rescan-First)

**Decision:** Require rescan for ANY edit; manual unlock after second Gemini pass

**Flow:**
1. User taps "Edit" → prompted to take new photo
2. Camera opens, user photographs item
3. Gemini reprocesses with fresh image
4. Before/after comparison shown
5. If still wrong → "Still incorrect?" unlocks manual edit
6. User edits fields, save with optimistic update

**Rationale:**
- Maintains data quality
- Users overestimate value/condition of their stuff
- Collects better training data (multiple photos per item)
- Manual edit is escape valve, not primary path

### 4. Update Strategy

**Decision:** Optimistic updates with revert on failure

**Rationale:** Modern apps feel instant. Firestore writes rarely fail for authenticated users. Error recovery is straightforward (revert + toast).

### 5. Delete Strategy

**Decision:** Hard delete with confirmation (no soft delete for MVP)

**Rationale:**
- Simplest to implement
- Users cataloging possessions rarely accidentally delete
- Confirmation dialog prevents mistakes
- Can add soft delete later if users request it

### 6. Bulk Operations

**Decision:** Bulk delete only; single-item edit (rescan requirement makes bulk edit awkward)

**Entry points:**
- Context menu (long-press) → single delete
- "Select" button in toolbar → multi-select mode → bulk delete

### 7. Context Menu

**Decision:** Long-press item → iOS context menu with Edit / Delete options

**Rationale:** Native iOS pattern (Messages, Photos app). Clean, discoverable.

### 8. Search

**Decision:** Client-side search across all text fields

**Fields searched:**
- name, category, subCategory, brand, model, color, material

**Rationale:**
- Zero cost, instant results, works offline
- MVP users will have <500 items (fits in memory)
- Can add server-side search when users hit scale issues

### 9. Offline Support

**Decision:** Online-only for creates/edits (MVP)

**Rationale:**
- Gemini processing is inherently online
- Simplifies architecture
- Can add offline queue post-MVP if users request it

### 10. Push Notifications

**Decision:** In-app status only (real-time Firestore listener handles it)

**Rationale:**
- Processing takes 5-15 seconds
- If app is open, user sees live update
- FCM setup is complexity for minimal MVP value

### 11. Photo Metadata

**Decision:** Full metadata capture, store only (no enforcement for MVP)

**Captured:**
- Location: GPS coordinates, altitude, timezone
- Time: capture timestamp (not upload time)
- Device: model, OS version, source type
- Authenticity: image hash (SHA-256), depth data presence, Live Photo flag
- Technical: lens type, image dimensions

**Storage:**
- Metadata struct → Firestore `items/{id}.photoMetadata`
- Live Photo motion clip → Cloud Storage `/items/{id}/motion.mov`

**Rationale:** Capture everything now, decide enforcement rules later with real data.

## Data Models

### Expanded Item Model

```swift
public struct Item: Identifiable, Codable, Equatable, Sendable {
    // Core (unchanged)
    public let id: String
    public let userId: String
    public let imageUrl: String
    public var status: ItemStatus
    public let createdAt: Date
    public var updatedAt: Date

    // Catalog data (expanded to match Gemini output)
    public var name: String?
    public var category: String?
    public var subCategory: String?
    public var brand: String?
    public var model: String?
    public var color: String?
    public var material: String?
    public var condition: ItemCondition?
    public var dimensions: String?
    public var quantity: Int?
    public var estimatedValue: Double?

    // AI metadata (read-only, not user-editable)
    public var confidence: ItemConfidence?
    public var processingNotes: String?

    // Edit tracking
    public var userEditedFields: [String]?
    public var lastRescanAt: Date?

    // Photo metadata
    public var photoMetadata: PhotoMetadata?
}

public enum ItemCondition: String, Codable, Sendable {
    case new
    case likeNew
    case good
    case fair
    case poor
}

public enum ItemConfidence: String, Codable, Sendable {
    case high
    case medium
    case low
}
```

### Photo Metadata Model

```swift
public struct PhotoMetadata: Codable, Sendable {
    // Location & Time
    public var latitude: Double?
    public var longitude: Double?
    public var altitude: Double?
    public var captureTimestamp: Date?
    public var timezone: String?

    // Device & Authenticity
    public var deviceModel: String?
    public var osVersion: String?
    public var sourceType: PhotoSourceType?
    public var imageHash: String?

    // Camera Technical
    public var lensType: String?
    public var hasDepthData: Bool?
    public var isLivePhoto: Bool?
    public var imageDimensions: CGSize?
}

public enum PhotoSourceType: String, Codable, Sendable {
    case camera
    case screenshot
    case savedFromWeb
    case imported
    case unknown
}
```

## Migration Plan

### Backfill Existing Items

Cloud Function to run once:

```typescript
async function migrateItems() {
  const items = await db.collection('items').get();

  for (const doc of items.docs) {
    const data = doc.data();
    if (data.catalog) {
      await doc.ref.update({
        name: data.catalog.name,
        subCategory: data.catalog.subCategory,
        brand: data.catalog.brand,
        model: data.catalog.model,
        dimensions: data.catalog.dimensions,
        quantity: data.catalog.quantity,
        // Keep existing fields, don't overwrite
        // Remove catalog field after verification
      });
    }
  }
}
```

### Rollout Steps

1. Deploy new iOS app with expanded Item model (backward compatible)
2. Deploy updated Cloud Function (writes to new fields)
3. Run backfill migration for existing items
4. Verify data integrity
5. Remove `catalog` nested field in cleanup pass

## Open Questions

1. **Home address for fraud detection:** Should we collect user's home address during onboarding for future GPS validation? (Deferred to post-MVP)

2. **Rescan cost:** Each rescan triggers Gemini processing (~$0.01-0.03). Monitor for abuse patterns. (Accept for MVP, add rate limiting if needed)

3. **Live Photo storage cost:** Motion clips add ~2-3MB per item. Monitor Cloud Storage costs. (Accept for MVP, can make optional later)
